总览 路径 A 路径 B 汇合点 异同对照

一个 WebApp，两条使用路径，汇合于同一产物

路径 A 用 GUI 表单分步创建：表单阶段 0 次后端调用 → 审阅按 Enter 才执行 → 发布走专家 API。 路径 B 与 expert-creator / expert-fixer 专家纯对话（无表单、自然语言创建或改进技能）。 两条路径在「发布」环节共用同一专家 API，最终收敛于同构产物：已发布专家 + evals 快照。 差异只在「入口与执行」，发布与交付物完全一致。

总览 SVG分支 → 汇合

单一入口分支成 A / B 两条路径，各自走完 3 段后在底部汇合。悬停任意节点可聚焦该路径，点击节点跳转到对应的界面 mock 卡片。

路径 A AGUI 表单驱动

结构化、分步、可审阅。核心窄门：表单阶段 0 次后端调用 → 审阅按 Enter 才执行 → 发布走专家 API。

A1 · 表单填写A
为什么零后端调用表单只是纯前端草稿：字段本地校验、即时反馈，不触网。真正的网络动作被推迟到「审阅执行」与「发布」两扇窄门之后。
A2 · 审阅执行A
为什么按 Enter 才执行审阅面板展示将写入的文件与 diff，确认动作由用户按 Enter 触发，杜绝「填完就执行」的意外副作用。Enter 是唯一的执行窄门。
A3 · 发布（专家 API）A+B
发布细节A 侧发布 = 表单审阅通过后的提交动作，走与 B 侧完全相同的专家 API，产物落到「已发布专家 + evals 快照」。

路径 B B专家纯对话

无表单、自然语言。expert-creator 负责创建技能、expert-fixer 负责改进 / 修复，全程对话驱动，发布同样走专家 API。

B1 · 纯对话（无表单）B
为什么没有表单对话本身就是窄门：用户只给一句话意图，其余由 expert-creator / expert-fixer 补齐细节，按需追问，不强迫填写完整表单。
B2 · expert-creator / expert-fixerB
两个专家的分工创建走 expert-creator（搭骨架 + 校验描述），改进 / 修复走 expert-fixer（修 references、补 evals）。都在对话内即时执行，无需表单。
B3 · 发布（专家 API）A+B
与 A 侧发布的差异仅入口不同（对话确认 vs 表单审阅），网络请求、API、落库产物完全一致——这就是「发布环节两条路径同构」的依据。

汇合点 A+B已发布专家 + evals 快照

无论从哪条路径进来，终点都是同一份可复现产物：一个已发布的专家 + 与之绑定的 evals 评测快照。

汇合 · 最终产物A+B
汇合点如何保证一致两条路径都向同一专家 API 提交、绑定同一 evals 快照 schema，因此「表单建的专家」与「对话建的专家」在发布后不可区分。
