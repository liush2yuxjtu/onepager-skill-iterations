AI 专家 WebApp · 双路径 onepager

结论：两条路径，一个终点。 路径 A（GUI 表单）表单阶段零后端调用、审阅按 Enter 才执行、发布走专家 API；路径 B（与 expert-creator / expert-fixer 纯对话）无表单、自然语言直接创建或改进技能。两者在发布环节共用同一专家 API，最终汇合为「已发布专家 + evals 快照」。

差异只在 表单 / 执行 / 发布 三个环节的自动化方式，终点契约唯一。

路径 A 专家编辑 · GUI 表单 草稿 · 零后端
按 Enter 审阅执行

零后端：表单阶段不产生任何 API 调用，未按 Enter 前只有浏览器本地草稿；审阅确认（Enter）才真正执行。

路径 B 与专家对话 无表单 · 自然语言
帮我创建一个「发布前校验」专家

expert-fixer 复核：修正 1 处规则冲突，其余通过。

对话即执行：无表单、无显式确认门，expert-creator / expert-fixer 边聊边生成或改进技能。

汇合

已发布专家 + evals 快照

两条路径发布后都落到同一份契约：可被专家 API 调用的已发布专家，并附带一份可复现的 evals 快照（能力评估结果随发布一同落库）。

表单 / 执行 / 发布 三环节异同

形态各异，终点相同：输入方式不同、执行门不同、发布通道唯一。

发布环节两路共用同一专家 API → 汇合为同一条契约，并落一份 evals 快照。

环节路径 A · GUI 表单路径 B · 专家对话判定
表单 结构化表单即 schema：字段 = 专家属性，草稿可本地保存。零后端：未按 Enter 前不产生任何 API 调用。 无表单。直接用自然语言向 expert-creator（创建）/ expert-fixer（改进）描述需求，由专家解析为技能草稿。 异
执行 显式确认门：审阅界面 按 Enter 才触发后端执行；执行前可无限改草稿，零副作用。 隐式执行：对话本身即执行，边聊边生成/修改，无单独的确认门。 异
发布 发布数据来自表单 JSON，调用专家 API。 发布数据来自对话产物，调用同一专家 API。 同
汇合 发布成功 → 写入「已发布专家 + evals 快照」：同一份发布契约、同一份可复现评估记录。 同
环节细则（按需下钻）
  • 表单阶段零后端：路径 A 的表单校验、字段映射全部在浏览器本地完成；后端只在 Enter 审阅执行后收到一次结构化 payload。
  • Enter = 执行闸门：路径 A 把「审阅」与「执行」解耦，Enter 是唯一的执行触发器，天然防误触，也便于审阅人逐字段复核。
  • 对话无闸门：路径 B 的每次助手回复都可能触发一次技能生成/改进，适合探索型需求；确定性弱于 A，但上手更快。
  • 同一条专家 API：无论产物来自表单 JSON 还是对话文本，发布都走同一个专家 API 通道，产物规范、校验、落库逻辑完全一致。
  • evals 快照：发布时强制生成或复用一次 evals 评估，作为该专家可复现的能力基线，后续改进可对照快照回归。
